# Демонстрационный стенд CRM для ООО «Акцент Плюс»

Учёт обращений клиентов на EspoCRM. Стенд собран для отчёта по преддипломной
практике и показа комиссии: комиссия входит по ссылке и видит работу системы
в реальном времени.

Данные на стенде вымышленные: 8 организаций, 8 контактных лиц, 30 обращений,
5 учётных записей. Реальные клиенты и персональные данные организации
не используются.

## Состав

| Компонент | Версия и роль |
|---|---|
| EspoCRM | свободная лицензия AGPLv3, модуль обращений (Cases), портал клиента |
| MySQL | 8.0, база `espocrm` |
| Контейнеры | `espocrm` (веб), `espocrm-daemon`, `espocrm-cron`, `mysql` |
| Демо-данные | дамп `dump/espocrm-demo.sql.gz` либо `seed_demo.py` через REST API |

## Что входит в комплект

В архиве нет `config-internal.php` и каталога `cache/`: это артефакты
конкретной установки, в них лежат пароль базы и ключ шифрования `cryptKey`.
При первом запуске контейнер EspoCRM создаёт их сам — из переменных `.env`
и случайного ключа. Поэтому свой ключ установки в комплект не попадает
и компрометировать его нечем.

Демо-дамп обеззаражен: в нём нет таблиц `auth_token` и `auth_log_record`,
то есть нет действующих сессий и журнала входов. Учётные записи демо-стенда
остались (на них ссылаются обращения), пароли у них — те, что были заданы
при наполнении скриптом `seed_demo.py`.

## Запуск локально

```bash
cp .env.example .env      # задать пароли и SITE_URL
docker compose up -d      # поднять базу и приложение
```

Установка завершается, когда в журнале появляется строка
`Installation completed successfully`:

```bash
docker compose logs -f espocrm
```

Система открывается по адресу `http://localhost:8080`. Порт публикуется
только на `127.0.0.1`, наружу стенд выставляется через обратный прокси.

## Наполнение демо-данными

Два взаимоисключающих пути, выбирайте один:

**1. Из дампа** — быстро, ровно те же 30 обращений, что на скриншотах:

```bash
bash deploy/restore.sh
```

**2. Скриптом** — медленнее, но доступы известны: на чистой установке
администратор получает пароль из `.env`, а пароли остальных пользователей
`seed_demo.py` генерирует случайно и печатает один раз в конце работы.

```bash
python seed_demo.py --url http://localhost:8080 --user admin --password <пароль из .env>
```

Важно: после `restore.sh` учётные записи приходят из дампа, поэтому пароль
администратора из `.env` уже не действует. Если доступы неизвестны без
restore — разверните стенд заново и используйте второй путь.

## Публикация для комиссии

1. VPS с российским центром обработки данных (2 vCPU, 2 ГБ памяти достаточно).
2. A-запись домена на адрес сервера, `SITE_URL=https://crm.example.ru` в `.env`.
3. Сертификат Let's Encrypt (certbot или средства хостера), HTTPS обязателен.
4. Порт 8080 закрыть наружу, публиковать через обратный прокси на 443.

## Учётные записи

| Логин | Роль |
|---|---|
| `admin` | администратор |
| `petrov` | руководитель сервисного отдела |
| `ivanova` | оператор приёма |
| `sidorov`, `kozlova` | исполнители |

Пароль администратора задаётся в `.env`, пароли остальных пользователей
`seed_demo.py` генерирует случайно и печатает один раз при создании; повторный
запуск скрипта пользователей не дублирует и пароли не меняет. В репозиторий
пароли не попадают; после `restore.sh` действуют те, что записаны в дампе.

## Обслуживание

- Резервная копия: `bash deploy/backup.sh` — дамп базы (без сессий и журнала
  входов) плюс копия тома данных EspoCRM. Копию тома нельзя публиковать:
  в ней `config-internal.php`.
- Обновление: `docker compose pull && docker compose up -d` после бэкапа.
- Перед обновлением рабочей системы проверять изменения на тестовом контуре.

## Что показывает стенд

- список обращений с номерами, статусами, приоритетами и ответственными;
- карточку обращения с клиентом, контактом, описанием и лентой истории;
- рабочий стол руководителя со сводкой и задачами;
- учётные записи сотрудников и разграничение прав.
